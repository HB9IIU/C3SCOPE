QO100 WEB SPECTRUM — PROJECT BRIEF FOR CODEX
Prepared for HB9IIU, 26 October 2026
Working name: QO100-WebSpectrum (not a final naming decision)

1. PURPOSE AND FIRST INSTRUCTION

Build a dedicated QO-100 DATV uplink spectrum and waterfall viewer using a
Seeed Studio XIAO ESP32-C3 connected to a PC by its native USB port. The user
operates the receiver through a webpage. No TFT is required.

Read this entire brief before implementing. Inspect the new workspace and any
AGENTS.md instructions. Begin by examining upstream ESP-WebSDR source and its
protocol implementation, then explain the proposed first implementation step.
Proceed with local, reversible implementation work within this scope. Do not
publish a repository, deploy a website, flash hardware, or change other projects
merely because this brief mentions those possibilities.

This is a NEW project, separate from the existing CYD firmware repository.
Do not convert, replace, or reorganize that existing repository.

2. BACKGROUND AND DECISIONS ALREADY MADE

The owner maintains two related projects:

A. Pocket QO-100 Spectrum Viewer:
https://github.com/HB9IIU/ESP32-CYD-pocket-qo-100-spectrum-viewer

It uses the ORIGINAL/classic ESP32 on 2.8-inch and 4-inch CYD boards. It captures
raw I/Q, performs FFT processing, and draws spectrum and waterfall on a TFT.
Its current signal pipeline uses 512 samples at 16 MS/s, with 31.25 kHz bin
spacing, a Hann window, power averaging and optional temporal burst filtering.
Its plotted RF window is 2401–2410 MHz. It includes indicative transmission
center-frequency and symbol-rate estimates. It is useful as an algorithm and
UX reference, not a firmware base to port blindly to C3.

B. C3CAST:
https://github.com/HB9IIU/C3CAST
https://github.com/HB9IIU/C3CAST/blob/main/docs/HOW_IT_WORKS.md

C3CAST is a local PC/browser application around an ESP32-C3 DATV transmitter,
based on SP8ESA's ESP32-DATV. The PC prepares video and DVB-S2 symbols; USB feeds
the C3, which produces RF. Its simple plug/connect/play experience is relevant
to this receiver's eventual packaging. Its BATC spectrum is a remote feed,
whereas this new application's primary data source is the local USB receiver.
Do not assume C3CAST code can be copied under the new project's license.

Initial uncertainty about C3 raw reception has been resolved at a practical
baseline level: the user flashed ESPARGOS ESP-SDR and reports that the existing
ESP-WebSDR viewer works perfectly with their ESP32-C3. The screenshot showed:
  - Receiving: ESP32-C3
  - On-chip spectrum mode, 2048 bins
  - Center frequency 2412 MHz
  - Nominal sampling/span 80 MS/s / 80 MHz
  - Manual gain index 0 out of 79
  - Analog filter setting 20 MHz
  - Live spectrum and waterfall

This confirms a working receiver/USB/browser chain. It does NOT establish
calibrated RF accuracy, a measured frame rate, continuous acquisition, or full
performance across the intended DATV window. Do not misreport those as tested.

Agreed direction:
  - Create a separate repository, preferably a fork of ESP-WebSDR.
  - Reuse the existing, working ESP-SDR firmware unchanged initially.
  - Adapt the frontend to a focused QO-100 workflow.
  - Python/Flask remains optional; it has been discussed, not mandated.
  - Do not implement DATV demodulation or video decoding in this project.

4. RF PURPOSE: LOCAL QO-100 DATV UPLINK MONITORING

This receiver observes nearby RF in the 2.4 GHz uplink band. It does not directly
receive the satellite's 10 GHz downlink. A downlink-equivalent axis is only a
frequency translation for operator convenience, not evidence of satellite RX.
Likewise, absence of local RF does not establish that a satellite slot is free.

Reference bandplan: AMSAT-DL/BATC QO-100 WB Bandplan V3, 6 February 2021:
https://amsat-dl.org/wp-content/uploads/2021/02/QO-100-WB-Bandplan-V3.pdf
https://wiki.batc.org.uk/QO-100_WB_Bandplan

Use the following project display limits:
  Uplink:               2401.000–2410.000 MHz
  Downlink equivalent: 10490.500–10499.500 MHz
  Mapping: downlink MHz = uplink MHz + 8089.500
  Reverse: uplink MHz = downlink MHz - 8089.500

Examples:
  2403.750 MHz uplink -> 10493.250 MHz downlink equivalent
  2405.250 MHz uplink -> 10494.750 MHz downlink equivalent
  2406.750 MHz uplink -> 10496.250 MHz downlink equivalent
  2409.750 MHz uplink -> 10499.250 MHz downlink equivalent

These are WB/DATV frequencies, not the separate QO-100 narrowband voice/CW band.
Before adding detailed allocations, beacon regions, recommended slots, or
symbol-rate restrictions, check the current primary bandplan and record its
version. Do not infer authoritative allocation boundaries from these examples.
The initial application is a receiver, not a transmitter frequency authorizer.

Store internal frequency values in integer Hz where practical. Format MHz
consistently; avoid floating-point rounding errors in ticks and cursor labels.
Label any secondary downlink axis explicitly as equivalent frequency.

5. HARDWARE AND ACQUISITION CONSTRAINTS

Primary device: Seeed Studio XIAO ESP32-C3, using native USB Serial/JTAG.
It differs from the classic ESP32 CYD: single-core RISC-V rather than dual-core
Xtensa, and native USB rather than a board-level USB-to-UART bridge.

Upstream lists C3 snapshot I/Q capture at 16, 40 and 80 MS/s, and on-chip FFT
spectra. Verify actual capabilities against the connected firmware. C3 capture
has gaps between snapshots; do not advertise continuous reception or gapless
I/Q. The nominal sample rate is not the USB data rate or the frame refresh rate.

Prefer sending processed spectra for normal operation. Raw I/Q capture may be
useful later for diagnostics, but is not needed for the first product.

Suggested initial QO-100 preset, to validate on hardware:
  - Capture center near 2406 MHz, matching the existing CYD approach.
  - 16 MS/s nominal capture span, containing the full 2401–2410 MHz view.
  - 2048 FFT bins if supported with acceptable responsiveness.
  - Crop the plot to the requested DATV window using actual frame metadata.

At 16 MS/s with 2048 bins, mathematical bin spacing is 7.8125 kHz. That is NOT
automatically the effective resolution bandwidth: window properties matter.
Do not describe a cropped view as a lower acquisition sample rate. Do not assume
the analog receiver response is flat across the full nominal digital span.
Verify gain, bandwidth, DC correction, and FFT orientation with a known source.

A center-frequency spike may be receiver DC/LO leakage. Preserve upstream
handling and offer an explicit display option if appropriate. Do not identify
such a spike as a real transmission without evidence. Do not silently erase
large regions that might contain a real signal.

6. ARCHITECTURE CHOICE

Preferred first milestone: keep upstream's direct browser-to-USB transport.
Serve the frontend over localhost or HTTPS as required by browser APIs. This
minimizes changes to an already demonstrated system and may need no Python.
Document supported/tested browsers; do not promise universal browser support.
Preserve the browser's device-selection and permission flow.

Optional later architecture for a C3CAST-style local application:
  ESP32-C3 <-> USB serial <-> Python backend <-> WebSocket <-> webpage

In that version Flask serves pages and configuration endpoints; a dedicated
serial worker owns the device and a WebSocket delivers live frames and status.
The browser must not also open the same device through Web Serial. A static
Flask launcher can also serve a direct-Web-Serial frontend; distinguish that
from moving serial ownership into Python.

Choose Python only for a concrete benefit such as application packaging,
device discovery, recording, or integration. Do not introduce it merely because
it was mentioned. Discuss the architecture after inspecting upstream, then
implement the smallest end-to-end slice.

Keep acquisition/transport, spectrum processing, rendering, and settings
separate enough that a future transport can be substituted without rewriting
the plots. Avoid a large speculative framework or premature generalization.

7. FIRST RELEASE: USER EXPERIENCE

The primary experience should be straightforward:
  Open application -> Connect receiver -> View QO-100 spectrum and waterfall.

Provide:
  - Clear connection state, receiver identity, errors, and reconnect action.
  - Large, responsive spectrum and waterfall sharing the same frequency axis.
  - Default 2401–2410 MHz view and an obvious Reset view action.
  - Uplink MHz labels; optional downlink-equivalent labels.
  - Frequency cursor with relative signal level.
  - Pause/resume and clear waterfall/max-hold controls.
  - Averaging, max hold, and sensible vertical scaling controls.
  - Gain and receiver bandwidth controls supported by firmware capabilities.
  - A compact advanced area for FFT size/sample rate and diagnostic settings.
  - Actual received frame rate, stale-data indication, and dropped/error counts
    where measurable. Do not show browser animation FPS as receiver frame rate.
  - Persisted user preferences with validation and a reset-to-default option.

Dark styling is a sensible initial direction, consistent with both spectrum
viewers, but final branding/layout is open. Prioritize readable axes, uncluttered
controls, and stable rendering. Support laptop and desktop windows first.
Do not require cloud accounts, analytics, or a remote backend.

Do not add transmitter Start/PTT controls. Do not combine C3CAST and the receiver
into one product in the first milestone. A remote BATC feed is optional future
work and must remain clearly separate from local measurements if ever added.

8. PLOTTING AND DATA INTEGRITY

Reuse upstream's working rendering and USB parsing where possible. Preserve
binary framing, CRC validation, and command/data serialization. Avoid parallel
commands that disrupt a capture response. Handle partial reads, disconnects,
device resets, corrupted frames, unsupported commands, and firmware differences.

Use requestAnimationFrame for rendering, but distinguish animation from new
measurements. Bound queues and favor recent data rather than building latency.
Do not run expensive DOM updates for every FFT bin. Resize canvas backing
buffers for device pixel ratio and handle layout changes cleanly.

Frequency bins must map consistently between trace, waterfall, cursor, zoom,
and annotations. Test orientation with a signal moved upward in frequency.
When reducing many bins to fewer pixels, choose aggregation deliberately so
narrow peaks are not accidentally hidden. Document detector behavior.

Use acquisition timestamps where available, otherwise host receipt timestamps
with that limitation stated. Waterfall time labels must reflect the chosen
time model, including pauses and missing data. Bound waterfall history memory.

Keep amplitude units honest: relative dBFS as provided/defined by upstream,
not calibrated dBm. Changing receiver gain or scaling affects comparisons.
Separate trace averaging, max hold, waterfall range, and receiver gain.

9. OPTIONAL SIGNAL ANALYSIS AFTER THE BASELINE

Useful follow-on features include occupied-bandwidth indicators, candidate
signal center frequency, and an indicative symbol-rate estimate.

Relevant common test rates include 125, 250, 333, 500, 666 and 1000 ksymbols/s;
C3CAST currently offers a subset. Never infer modulation, FEC, MER, BER, or
successful DATV decoding merely from the envelope of a spectrum.

The CYD's symbol-rate algorithm is an empirical reference, not a general
measurement standard. Its threshold, bin spacing, smoothing, and normalization
must not be copied without evaluating the new spectrum data and detector.
Bandwidth depends on pulse shaping/roll-off; occupied bandwidth is not simply
equal to symbol rate. Show uncertain/absent results honestly and avoid forcing
every arbitrary signal into the nearest nominal DATV rate.

Develop analysis against saved captures and known transmitter settings. Keep
these features out of the critical path for first live spectrum operation.

10. PERFORMANCE GOALS AND TESTING

Aim for a responsive live display. 20–30 real spectrum updates per second is a
desirable exploration target, not a promise or required result without hardware
measurements. Report achieved rates for each tested configuration. Benchmark
the upstream viewer before attributing improvements to our application.

Suggested hardware validation:
  1. Connect the already-flashed C3; read identity and supported capabilities.
  2. Capture a stable baseline with no intentional nearby test transmission.
  3. Use a second C3/C3CAST or Pluto as a known local signal source.
  4. Verify signal appearance/disappearance when transmission is toggled.
  5. Verify frequency movement and DATV width changes at known symbol rates.
  6. Check both edges of the 2401–2410 MHz display window.
  7. Exercise gain and bandwidth settings and look for clipping/alias artifacts.
  8. Measure frames per second, latency, transfer errors and prolonged stability.
  9. Unplug/replug, pause/resume, resize, reset view, and restart the application.

Use low-power over-the-air testing or appropriate RF attenuation. Never connect
a transmitter output directly to the C3 RF connector. A dedicated receiver board
is preferable so tests do not overwrite the user's working C3CAST transmitter.

Meaningful software checks:
  - Known binary frame fixtures, partial reads, CRC failures and recovery.
  - Frequency translation and exact pixel/bin mapping at range boundaries.
  - Settings validation and compatibility fallbacks.
  - Bounded buffering and stale-data handling.
  - Browser checks for connection/error states and responsive rendering.

Use recorded or synthetic frames when hardware is unavailable, clearly marked
as replay/demo. Never claim hardware validation from simulated data. Keep
test scope proportional to changes; use upstream tests when available.

11. DEVELOPMENT PHASES AND DELIVERABLES

Phase 1 — Establish the baseline
  Inspect upstream source/license/protocol; record commit and supported firmware.
  Run the unmodified frontend locally and document how to start it. Preserve
  the functioning connect/capture/display workflow before redesigning.

Phase 2 — Focus the interface
  Add the QO-100 preset, DATV display crop, consistent axes, and project branding.
  Keep proven receiver controls accessible. Deliver a working local viewer.

Phase 3 — Refine usability and robustness
  Improve display controls, preferences, error/reconnect behavior, and relevant
  measurements. Test known RF signals and record performance/results.

Phase 4 — Optional packaging and analysis
  Decide whether a Python/Flask launcher or serial backend materially helps.
  Add packaging, recording, and signal estimation only as agreed extensions.

Expected repository documentation:
  README with purpose, hardware, setup, browser requirements and connection steps.
  Architecture note identifying USB ownership and data flow.
  Upstream provenance, firmware compatibility and applicable license notices.
  RF limitations and distinction between local uplink and equivalent downlink.
  Validation notes separating automated, replay, and real hardware results.
  Clear development commands and any build/package instructions actually used.

12. FIRST-MILESTONE ACCEPTANCE CRITERIA

An already-flashed XIAO ESP32-C3 can connect to our local webpage using unchanged
ESP-SDR firmware. Real spectrum and waterfall data appear, cropped to the DATV
uplink window. Cursor and both plots agree on frequency. Device disconnects are
handled visibly without an unbounded backlog or frozen misleading live status.
An operator can adjust supported gain settings, pause, and reset the view.
The README explains exactly how to run it. Attribution is preserved. Any
unverified behavior is stated explicitly.

13. WORKING STYLE FOR CODEX

Treat this brief as a project handoff, not proof that all implementation choices
are finalized. Preserve the user's existing work. Make incremental changes with
short progress updates. Ask focused questions only for decisions that materially
change scope or need unavailable information; inspect connected/local context
first. Do not assume missing hardware is connected or that flashing is desired.

Do not spend time building a replacement SDR firmware or decoding DATV video.
Do not promise higher RF sensitivity, calibrated power, continuous sampling, or
frequency resolution improvements solely from a larger plot or smoother drawing.

The core opportunity is already demonstrated: a small ESP32-C3 receiver, one
USB cable, and a useful browser spectrum display. Build a focused QO-100 tool on
that working foundation.
